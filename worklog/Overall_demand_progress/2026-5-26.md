### 3. sequence_train 课程策略（已锁定）
- 启用时机：`10k iteration`
- 比例课程：`10k -> 30k`，`0% -> 30%`
- 长度课程：
  - 阶段 1：长度 `2`
  - 阶段 2：长度 `2~4`
  - 阶段 3：长度 `2~6`
  - 每阶段 `5k iteration`
- 模板刷新：每 `1k iteration`
- 每次约 `16` 条训练模板
- 抽样规则：
  - 候选池来自 `single_train_specs()`
  - 无放回抽样
  - 按 `terrain_id` 排序
  - 当前默认不允许重复地形，但代码预留允许重复的参数
- 相邻性/能力约束：V1 不加
- 缓冲段：相邻地形段之间插入 buffer，长度在 `1m~3m` 间随机采样
- 统一朝向：目标统一为 `+Y`
- `Z` 不主动重对齐，但必须做检查

### 4. sequence_eval 策略（已锁定）
- `sequence_eval` 当前阶段**不进入训练主循环**
- **不参与参数更新**
- 先作为**独立手动 eval / play 脚本**
- 先在关键训练阶段手动评估；后续如有需要，再升级成自动 periodic eval
- 训练期评估地形必须是训练地形子集
- 当前未进入训练的 4 个困难地形只保留为 future benchmark 接口，不进入当前训练期评估

### 5. 当前验收指标（已锁定）
- 一级指标采用“双指标并重”：
  - 完整通过率
  - 分段通过率

## 三、对 sequence_generator 第一版实现的审查结论

### 审查对象
- 实现文件：
  - `source/obstacle_crossing/obstacle_crossing/terrain/sequence_generator.py`
- 实现说明：
  - `worklog/2026-5-26/implementation_Details_of_sequence_generator.md`

### 总体评价
**结论：当前 `sequence_generator.py` 的第一版实现是“可用且较为可靠”的，但还属于 V1 能力层，不是全链路落地终态。**

换句话说：
- 它已经不是空骨架
- 能真实生成训练侧 sequence 模板池、拼接长地形 mesh、导出 STL + YAML
- 能产出 assignment / command / reward 将来需要消费的元数据
- 但它还未接入训练主循环、真实 runtime terrain indexing、独立 eval 脚本与 physics apply

### 当前实现已验证可工作的能力
本次已做最小验证，结果表明：
1. 能正常构建训练模板池（示例模板数=2）
2. 能按当前 iteration 输出正确的 active length range
3. 能按规则采样 terrain 组合、buffer 长度和 sequence id
4. 能输出 sequence warnings（如 Z 边界 mismatch、朝向告警）
5. 能导出：
   - `sequence_<id>.stl`
   - `sequence_<id>.yaml`

### 当前实现的可靠性优点
1. **职责边界基本正确**
   - 没有把 registry/layout/assignment 的职责混到 generator 里
   - sequence 课程与抽样逻辑在 generator 自己内部实现，没有依赖 layout 私有方法
2. **数据结构较完整**
   - 已包含 segment、template、template pool 三层结构
   - 已保存 command/capability/physics/collision 元数据
3. **输出形式符合当前 V1 决策**
   - 以 STL + YAML 为主
   - 预留 USD backend 接口（当前为 `NotImplementedError`）
4. **检查逻辑不是静默失败**
   - Z 对齐、边界高度等问题会形成 warning
   - 对后续调试非常重要
5. **与现有 assignment 的未来对接方向正确**
   - generator 已产出 assignment 需要消费的 metadata 基础

### 当前实现的局限与风险
1. **当前 buffer 只是“间距+区间”，不是实体 connector mesh**
   - 这意味着长地形物理连续性在 connector 处还不算最终版本
   - 后续如果 sequence_train 真要进入真实训练场景，buffer 很可能需要升级成真实几何
2. **`+Y` 统一朝向逻辑目前采用简单的 extent 判断旋转**
   - 对当前 6 地形可能够用
   - 对未来复杂地形（楼梯、L弯、crawl）不一定稳
   - 后续可能需要 per-terrain orientation override
3. **Z 不重对齐但仅告警**
   - 目前生成器采用“检查+warning”而不是“强制修复”
   - 对当前阶段是合理的，但如果训练中确实出现明显接缝，后续需要加入 strict mode 或自动修正策略
4. **assignment 尚未真正消费 template metadata 文件**
   - 现在 generator 和 assignment 仍然是“同向设计”，还没形成闭环 runtime
5. **sequence_train 的真实训练场景接入仍未完成**
   - generator 已经能生产模板，但还没真正接到训练时的 scene / terrain loader / env binding

### 审查结论（可直接给实现终端）
- **可以接受当前实现作为 V1 版本继续往下推进**
- **不建议现在返工重写 generator**
- 后续工作重点应转向：
  1. 让 assignment 真正消费 sequence template 元数据
  2. 让训练/评估入口能加载 sequence 模板
  3. 视训练效果再决定是否升级 buffer 为实体 connector mesh

## 七、基于当前地基，terrain 侧还需要实现的内容（补充）

### 1. assignment 与 template 的正式闭环
当前 `terrain_assignment.py` 已能表达 env -> role / terrain / capability / profile 的查询，但还没有真正消费 `SequenceTemplateRecord` / `SequenceTemplatePool`。

后续 terrain 侧需要实现：
- env -> `sequence_id` 的正式绑定
- env -> `segment_ranges_y` 的查询
- env -> `physics/collision profile keys` 的 template 级映射
- 从“逻辑 round-robin 绑定”升级到“真实 template 绑定”

### 2. sequence_train 真实模板进入训练场景
当前 `sequence_generator.py` 已能生成真实 sequence 模板，但 terrain 侧还没把这些模板真正接入训练场景。

后续需要明确并实现：
- 训练场景如何加载 16 条 sequence 模板
- `sequence_train` env 如何共享这些模板
- single terrain 与 sequence terrain 在同一训练框架下如何共存
- 与当前 terrain importer / scene setup 的衔接方式

### 3. generator 输出与 command / reward / observation 的对接
terrain 侧后续不仅是几何问题，还需要把 sequence metadata 真正交给下游模块使用。

后续需要支持：
- command 根据当前 sequence / segment 读取 profile
- reward 根据 segment / sequence 边界统计完整通过率和分段通过率
- observation / debug 输出当前 env 绑定的 sequence 信息

### 4. 独立手动 sequence_eval 地形入口
虽然 `sequence_eval` 当前已确定不进入训练主循环，但 terrain 侧仍需提供 eval 所需的基础入口：
- 固定 benchmark 模板池
- 随机 benchmark 模板池
- 供 `play/eval` 脚本直接加载的 sequence 几何与 metadata 目录结构

### 5. connector / buffer 的几何实体化（后续增强项）
当前 buffer 仅是“间距 + 区间记录”。如果训练中暴露明显接缝问题，terrain 侧后续要准备升级为：
- 真正的 connector mesh
- 与前后 segment 一致的边界约束
- 可能的 profile / collision 继承规则

### 6. per-terrain orientation override 与 Z 对齐增强
当前统一朝向主要依赖 extent 判断，对未来困难地形（如 stairs / crawl / L-bend）未必足够稳。

后续 terrain 侧可以逐步增强：
- per-terrain orientation override table
- strict mode 对齐检查
- 必要时的自动修正策略

### 7. USD backend（后续增强项）
当前 generator 已预留 `USD` backend 接口，但还未实现。
terrain 侧后续如需要与 Isaac Sim / USD 工作流更紧密集成，应补齐：
- USD 输入读取
- USD sequence 输出
- 对应 metadata 一致性

### 8. 当前 terrain 侧优先级建议
基于今天的主线推进，terrain 侧下一步优先级建议为：
1. assignment 消费 template
2. sequence template 接入训练场景
3. command/reward/observation 读取 sequence metadata
4. 独立手动 eval 所需的模板加载入口
5. buffer 实体化 / orientation override / USD backend

### 9.个人想法

我觉得如果是iteration内动态加载，这个时候，后期如果需要修改的话，需要修改runtime的逻辑。而如果sequence_generator在外    部预生成再加载，似乎模块之间的独立性更好？也更好维护？也就是说，我的粗略想法是：将长地形生成编写成一个长地形生成器，    生成器运行会自动生成符合地形长度数量要求，以及随机缓冲通过区长度的长地形，这个长地形生成器需要接收的参数应该就是训练    时的iteration等用来帮助确定长地形包含多少个单地形。也就是确定2/3/4/5/6应该到了哪个阶段。长地形生成器会将生成的地形放    到一个缓存长地形库中，而单地形我记得目前也存在一个单地形缓存库。那么env在随机分配env的terrain时，可以按照我们设定的比   例，以及环境总数，区单地形缓存库和长地形缓存库中随机实例化出相应数量的单地形和多地形匹配到env中。也就是例如4096个地形   ，目前的阶段，长地形由2个单地形组成，比例是90%和10%，那么长地形生成器就会生成由随机两个单地形组成的长地形并放入长地形   缓存库，然后env就会将10%的4096个地形，去长地形缓存库中采样，另外90%的环境会去single地形库中采样。然后每隔固定的iteration又会刷新长地形缓存库。
